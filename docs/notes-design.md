# 笔记服务端设计

笔记取代 iOS 的资产页。笔记和已保存的文件在同一个画廊按时间展示，支持置顶。对话里可以把助手消息整理成笔记，也可以把已保存的笔记带回对话。Lulu 对已有笔记的编辑先生成预览，用户右滑后才生效。

## 数据和归属

沿用 Bot 内的 Pi Durable Docs 和 SQLite。以 Bot 为范围保存笔记，以对话为范围记录来源和候选卡的位置。正文版本和候选按 ID 单独存储，画廊索引只保留列表展示所需的摘要。手动编辑可防抖保存，同一内容的重复请求不增加版本。

| 记录 | 主要字段 | 用途 |
| --- | --- | --- |
| 笔记 | `noteId`、`currentRevision`、`createdAt`、`updatedAt`、可选的来源 `conversationId + callId` | 稳定身份、画廊排序，以及回到原对话。 |
| 笔记版本 | `noteId + revision`、标题、Markdown 正文、有稳定 ID 的清单项、带版本的附件引用 | 手动保存或接受编辑后生成新版本。已接受的旧版本可用于还原历史对话上下文和展示修改前的内容。 |
| 候选卡 | `proposalId`、`requestId`、对话 ID、`create / edit`、候选内容、状态。编辑另有 `noteId + baseRevision` | 内容和基准版本在卡片生成时固定。接受结果记录目标 `noteId + revision`。 |
| 画廊索引 | 笔记摘要、更新时间、按卡片身份记录的 `pinnedAt` | 分页展示。文件继续从现有资产清单读取，由服务端和笔记摘要合并。 |

附件保留 `artifact://name@version`，复用现有文件预览和下载接口。已有资产直接进入画廊，无须转换或搬文件。笔记引用固定文件版本，资产卡继续按现有规则显示该文件最近一次保存的版本。资产卡置顶用文件名作稳定身份。移除已保存的资产卡沿用现有语义，引用同一文件的笔记仍可以打开附件。底层文件另行删除时，附件显示不可用，笔记依然可读。

画廊使用服务端时间。笔记按内容更新时间排列，资产按保存时间排列。置顶作为独立排序字段，置顶或取消置顶时，原时间分组保持稳定。客户端沿用现有本地时区分组。

## 从对话存入笔记

1. 用户长按助手消息，客户端发 `note.generate`，带 `requestId` 和当前对话中那条已交付消息的 `callId`。
2. 服务端验证来源，取完整 Markdown 和该条消息之前有助于理解它的有限上下文。旧消息走历史读取。任务持久化这次的来源范围和所选内容，恢复时使用同样的输入。
3. 用 Pi Durable 后台任务运行专用子对话。子对话只接收本次素材，输出结构化笔记草稿，工具范围限于提交草稿。服务端校验内容和附件引用。普通委派的结果会重新送回主对话，这里直接产出候选卡，用户可以继续原来的聊天。
4. 服务端在同一事务中保存候选内容和聊天条目 `lulu.note.proposal`。条目按生成完成时追加到对话，带回原消息的引用。历史分页和重连都能恢复那张卡。同一个 `requestId` 重放返回原任务，同一来源已有进行中的任务时也复用。失败或超时保留任务状态，在线客户端收到失败结果，用户明确重试时再开新任务。
5. 右滑发 `note.accept`。同一事务创建笔记、写首个版本、更新画廊索引并保存接受凭据。双滑、掉线重试或两台设备同时接受同一张卡，返回同一篇笔记。

## 从笔记带回对话

点击「带回对话」后，缩略卡先作为本地输入草稿的一部分。发送时，现有 `prompt.submit` 增加可选的 `noteRef: { noteId, revision }`，服务端在接收消息的事务里校验归属和显示版本，把精确版本绑定到这次 submission。

输入框可以继续携带这张缩略卡，直到用户点 × 或换一篇。每次发送都使用当时卡片显示的版本。点 × 之后的新消息停止附带笔记，之前已发送的引用仍属于聊天历史。由服务端根据引用解析内容，客户端无需在消息里另传一份正文。模型只在这次请求中收到笔记快照。正文及文件内容作为引文数据，附件默认只提供名称和版本引用，按需走现有读取能力。

如果另一台设备已更新笔记，讨论仍可使用用户眼前那一版。客户端可刷新卡片到新版本。发送重试和服务端补发都沿用原始 submission 的引用。排队或追加消息时按 submission 区分引用，避免把上一条消息的笔记绑定到下一条。

## Lulu 提议编辑笔记

当前请求附带笔记时，Lulu 可以调用专用工具 `propose_note_edit`。服务端从已绑定的上下文决定目标笔记和基准版本，目标不明确时先在对话里确认。模型只提交要替换的标题、正文或清单字段。首版保留附件，未提交的字段继承原版。工具直接生成一张更新候选卡，不弹授权。卡片可以预览修改前后。工具调用重放时复用原候选。

用户右滑后，服务端在同一事务内处理接受凭据和版本校验。

1. 同一张卡已有接受凭据时，返回原结果，即使这篇笔记之后又修改过。
2. 当前版本等于卡片的 `baseRevision` 时，写入新版本、更新画廊并记录接受结果。
3. 期间如果有手动编辑或另一张卡先被接受，返回 `revision_conflict`。原笔记保留当前内容，旧卡标为过期。用户可以基于最新版重新生成。手动保存也带 `baseRevision`，发生冲突时客户端保留输入草稿。

例如 Lulu 基于第 3 版提议修改，用户随后在笔记页直接保存了第 4 版。再右滑旧卡时会提示原笔记已改动。若旧卡已先写出第 4 版，网络重试会返回那次成功结果，无须再写一版。

## 客户端协议

| 接口 | 契约 |
| --- | --- |
| `GET /notes`、`GET /notes/:noteId` | 通过现有 Bot 私有 API 读取画廊摘要和笔记详情。列表分页，正文按需读取。 |
| `note.create`、`note.update`、`note.pin` | 使用现有带 `requestId` 的 WebSocket 命令。手动编辑带基准版本，置顶传目标布尔值。 |
| `note.generate`、`note.accept` | 生成返回任务标识，完成时通过对话条目下发卡片。接受返回 `noteId + revision` 或结构化冲突信息。 |
| `prompt.submit` 的可选 `noteRef` | 复用现有消息发送、排队和重试。普通消息的请求格式无需变动。 |

笔记列表与详情使用版本或变更游标刷新。在线客户端通过能力协商接收变更通知，重连时重新对齐版本。旧客户端继续使用现有资产接口和聊天协议。聊天记录保存候选快照的标识和展示所需摘要，卡片状态按候选 ID 更新。候选内容在预览或确认时从服务端读取，避免把笔记全集加入聊天状态。

## 实施顺序和验证

1. 先接入笔记版本和画廊读取，跑通手动创建、编辑、置顶、既有资产展示和附件读取。
2. 接入生成任务、候选卡和接受事务，验证重连恢复、历史分页、生成失败重试和重复接受。
3. 接入 `noteRef` 和编辑工具，验证普通聊天、带笔记讨论、清除引用、修改预览、并发版本冲突，以及旧客户端的资产操作。
